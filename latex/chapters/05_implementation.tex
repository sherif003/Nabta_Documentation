\section{Overview}
\label{sec:impl_overview}

This chapter documents the practical realisation of the system design described in \chapref{chap:design}. It encompasses the selection and justification of the full technology stack, a description of the development environment and tooling, an account of the deployment configuration, and illustrative references to key interface screens. The implementation phase proceeded in three parallel workstreams---AI model development, backend service construction, and frontend application development---coordinated through a shared Git repository and a sprint-based project management workflow.

\section{Development Environment}
\label{sec:dev_env}

Model training was performed on cloud GPU platforms (Google Colab Pro+ and Kaggle Notebooks) utilising NVIDIA A100 and T4 GPUs with 16GB and 40GB of VRAM respectively. The classification CNN training run of 100 epochs on the 116,000-image corpus required approximately 14 hours of wall-clock time on an A100 instance. U-Net training completed in approximately 4 hours, and YOLOv8 fine-tuning in approximately 2 hours.

Local development was conducted on workstations running Ubuntu 22.04 and Windows 11 with Python 3.11 virtual environments. The backend was developed using \textbf{VS Code} with the Pylance language server and the REST Client extension for endpoint testing. Frontend development used VS Code with the ESLint and Prettier extensions to enforce code style consistency.

\section{Key Implementation Details}
\label{sec:impl_details}

\subsection{Model Serialisation and Loading}
\label{subsec:model_load}

Trained model weights are serialised in the following formats:
\begin{itemize}[leftmargin=*]
  \item \textbf{YOLOv8:} Ultralytics \texttt{.pt} checkpoint format.
  \item \textbf{U-Net:} PyTorch \texttt{state\_dict} serialised via \code{torch.save()}.
  \item \textbf{Custom CNN:} PyTorch \texttt{state\_dict} serialised via \code{torch.save()}.
\end{itemize}

At FastAPI server startup, all three models are loaded into a singleton \code{MLManager} instance, which pins model tensors to the available GPU device (falling back to CPU if no CUDA device is detected). This singleton pattern eliminates per-request model loading overhead, which would otherwise add multiple seconds to inference latency.

\subsection{Asynchronous Pipeline Execution}
\label{subsec:async_exec}

FastAPI's \code{async def} route handlers enable the server to accept new HTTP connections while awaiting I/O-bound operations (database reads/writes, Cohere API calls). CPU-bound model inference operations are dispatched to a thread pool executor via \texttt{asyncio.run\_\allowbreak in\_\allowbreak executor()} to prevent blocking the event loop:

\begin{lstlisting}[language=Python, caption={Asynchronous Model Inference Dispatch}, label={lst:async_infer}]
import asyncio
from concurrent.futures import ThreadPoolExecutor

executor = ThreadPoolExecutor(max_workers=4)

async def run_pipeline(image_tensor):
    loop = asyncio.get_event_loop()
    result = await loop.run_in_executor(
        executor,
        ml_manager.run_full_pipeline,
        image_tensor
    )
    return result
\end{lstlisting}

\subsection{Grad-CAM Implementation}
\label{subsec:gradcam_impl}

\gradcam is implemented using a forward hook registered on the final convolutional layer of the CNN to capture activation maps, and a backward hook to capture the corresponding gradients:

\begin{lstlisting}[language=Python, caption={Grad-CAM Hook Registration}, label={lst:gradcam}]
class GradCAM:
    def __init__(self, model, target_layer):
        self.model = model
        self.activations = None
        self.gradients = None
        target_layer.register_forward_hook(self._save_activations)
        target_layer.register_backward_hook(self._save_gradients)

    def _save_activations(self, module, input, output):
        self.activations = output.detach()

    def _save_gradients(self, module, grad_in, grad_out):
        self.gradients = grad_out[0].detach()

    def generate(self, input_tensor, class_idx):
        output = self.model(input_tensor)
        self.model.zero_grad()
        output[0, class_idx].backward()
        weights = self.gradients.mean(dim=(2, 3), keepdim=True)
        cam = (weights * self.activations).sum(dim=1, keepdim=True)
        cam = torch.clamp(cam, min=0)
        cam = F.interpolate(cam, size=input_tensor.shape[2:],
                            mode='bilinear', align_corners=False)
        cam = cam - cam.min()
        cam = cam / (cam.max() + 1e-8)
        return cam.squeeze().cpu().numpy()
\end{lstlisting}

\subsection{RAG Knowledge Base Ingestion}
\label{subsec:rag_ingest}

The knowledge base was constructed by collecting 847 agronomist-authored treatment documents spanning all 102 disease classes, converted from structured agricultural manuals and curated field guidelines. Each document was split into 512-token chunks with 64-token overlap using LangChain's \code{RecursiveCharacterTextSplitter}. Chunks were embedded using the Cohere \code{embed-multilingual-v3.0} model (1024-dimensional output) and indexed in a persistent Chroma vector store.

\subsection{Internationalisation (i18n)}
\label{subsec:i18n}

Bilingual support for Arabic and English was implemented using \textbf{i18next} with the \texttt{react-\allowbreak i18next} bindings. Translation files are maintained as JSON dictionaries for all UI strings. The chatbot's language mode is communicated to the backend as a request header (\code{X-Language: ar} or \code{X-Language: en}), which is incorporated into the system prompt to instruct the Cohere model to respond in the specified language.

\section{Deployment}
\label{sec:deployment}

\subsection{Backend Deployment}
\label{subsec:be_deploy}

The FastAPI backend is containerised as a Docker image based on \code{python:3.11-slim}. The production container includes:
\begin{itemize}[leftmargin=*]
  \item Gunicorn configured with 4 Uvicorn workers.
  \item Nginx sidecar container for HTTPS termination and static file serving.
  \item Model weight files embedded in the container image or mounted via a Cloud Storage volume.
\end{itemize}

The container is deployed to \textbf{Google Cloud Run}, providing automatic scaling from zero to multiple concurrent instances based on request volume, with a minimum instance count of one to eliminate cold-start latency.

\subsection{Frontend Deployment}
\label{subsec:fe_deploy}

The React.js application is built using Vite's production build pipeline (\code{vite build}), producing an optimised static asset bundle. The bundle is deployed to \textbf{Firebase Hosting}, which serves assets from Google's global CDN with automatic HTTPS enforcement and custom domain support.

\subsection{CI/CD Pipeline}
\label{subsec:cicd}

A GitHub Actions workflow automates the following pipeline on every push to the \texttt{main} branch:
\begin{enumerate}[leftmargin=*, label=\arabic*.]
  \item Run Python unit and integration tests (pytest).
  \item Run ESLint and TypeScript type-checking on the frontend.
  \item Build and push the backend Docker image to Google Container Registry.
  \item Deploy the new image revision to Cloud Run.
  \item Build the React.js production bundle.
  \item Deploy the bundle to Firebase Hosting.
\end{enumerate}
